설비의 한계까지 계산해서 파는
VPP 입찰 시스템

기존 VPP(가상발전소) 거래는 설비 상태를 언제나 100% 정상이라 가정합니다. 이 프로젝트는 고장·열화 리스크를 목적함수에 직접 넣고, AI는 후보를 제안하고 코드가 숫자를 검증하는 이중 승인 구조로 최적 입찰을 추천하는 Human-in-the-Loop 시스템입니다.

  • 시스템 전체 아키텍처 기획 — 데이터 흐름·검증 단계·재시도 게이트 구조
  • 주제 선정 및 문제 정의 — 제주 VPP 페인포인트 발굴
  • 트레이드오프 목적함수 및 고장확률 배수 모델 설계
  • 이중 AI 교차검증 + 규칙기반 재계산 대조 + 재시도 게이트로 이어지는 검증·피드백 루프 설계
  • 시나리오 근거 뷰어(프론트엔드) 디자인
  • 총괄 진행 및 발표
정직하게 밝히면: n8n 노드의 실제 구현, Slack 알림 UI 코드, 외부 데이터 입력 파이프라인은 팀원이 맡았습니다. 이 페이지는 제가 설계한 로직과 검증 구조를 중심으로 정리했습니다.
01 · 문제 정의

제주는 이미 VPP 실험장이지만, 거래 로직은 설비를 보지 않는다

제주는 신재생(태양광·풍력) 비중이 높아 전력이 과잉되면 발전을 강제로 멈추는 출력제어(Curtailment)가 빈번하고, 국내에서 가장 먼저 VPP·신재생 전력 거래 시범 시장이 열린 지역입니다.

그런데 기존 VPP 거래 알고리즘은 설비 상태를 항상 '100% 정상'이라 가정합니다. SMP(전력 가격)가 오르면 ESS를 무리하게 고출력 운전시키고, 그 결과 과열·미세 이상이 무시된 채 급격한 열화로 이어집니다.

Pain Point

당장의 판매 수익보다 설비 고장으로 인한 손실(정비비용 + 계약 불이행 페널티)이 더 큽니다. 무리한 고출력 운전으로 생긴 급격한 열화·고장은 며칠 치 전력 판매 이익을 단번에 상쇄시킵니다.

02 · 해결책

목적함수 하나로 이 문제를 다시 정의했다

전력 가격만 보고 100% 출력으로 질주하는 기존 로직에, 설비의 마모도와 고장 확률을 정량적으로 계산하는 로직을 더했습니다.

\[ \Pi(r) = G(r) - R(r) \]
실질 순이익 Π(r) = 전력 판매 수익 G(r) − 고장위험·열화 리스크 비용 R(r) (r = 출력 비율)
01
설비 이상 징후 스코어 측정
02
고장 확률 P_failure 산출
03
출력 구간별 순이익 비교
04
최적 시나리오 자동 추천
03 · 시스템 아키텍처

AI는 제안만 하고, 숫자는 코드가 계산한다

n8n 위에 8단계 파이프라인으로 설계했습니다. 각 단계가 AI 판단인지 결정론적 코드인지 사람의 승인인지를 명확히 나눈 것이 이 아키텍처의 핵심입니다.

자동 수집

데이터 입력

SMP 전력가격 API + 제주 기상청 API(기온·하늘상태·풍속) + ESS BMS 센서(Google Sheets, 온도·전압·C-rate)

규칙기반 코드

PHM Engine

온도·진동·전류·압력 4개 신호를 가중합(0.35/0.35/0.15/0.15)해 고장확률을 산출. Critical 신호가 하나라도 있으면 최소 0.75로 보정하는 등 규칙기반 로직.

AI 제안

Strategy Proposer

LLM이 검토할 가치가 있는 출력비율 후보를 제안. 숫자는 직접 계산하지 않습니다 — 손익 계산은 다음 단계의 몫으로 명시적으로 넘깁니다.

결정론적 코드

Trade-off Optimization Engine

목적함수 Π(r)=G(r)−R(r)로 각 후보의 매출·리스크비용·순이익을 코드가 직접 계산.

AI 검증

Safety × Financial Reviewer

서로 다른 관점을 가진 두 LLM 리뷰어가 같은 시나리오를 교차검증. 안전 리뷰어는 정비기록·PHM 우선순위로, 재무 리뷰어는 이미 계산된 숫자만 인용하도록 설계.

결정론적 코드

규칙기반 재검증

AI 응답의 스키마 검증 + 같은 공식으로 독립적으로 재계산해 원 값과 대조(diff-check) + 물리적 타당성 + 후보 다양성 검증.

제어 로직

재시도 게이트

반려되면 최대 1회만 자동으로 재제안. 그래도 통과하지 못하면 그대로 사람에게 넘깁니다.

사람

Human-in-the-Loop 승인

Slack 카드로 A/B/C 시나리오 제시 → 관리자 원클릭 승인 → Google Sheets 자동 기록.

04 · 검증 · 피드백 루프 설계

이 시스템의 핵심은 계산이 아니라 검증이다

해커톤에서 제가 가장 많은 시간을 쓴 부분입니다. AI를 한 번 믿고 끝내는 대신, 실패 모드마다 다른 방식으로 잡아내는 다층 검증 구조를 설계했습니다.

① 이중 관점 교차검증

같은 시나리오를 Safety Reviewer(정비기록＞PHM＞운전환경＞시나리오 순으로 판단)와 Financial Reviewer(표에 이미 계산된 숫자만 인용, 재계산 금지)가 서로 다른 기준으로 각각 검토합니다. 하나의 AI 판단에 기대지 않고, 서로 다른 실패 모드를 잡도록 프롬프트를 설계했습니다.

② AI는 제안자, 결정은 코드

LLM이 만든 응답 속 금액·확률 숫자는 하나도 그대로 신뢰하지 않습니다. 규칙검증2 노드가 동일한 공식으로 완전히 독립적으로 재계산해 원래 값과 대조하고, 오차가 나면(허용오차 1원) 그 자리에서 반려합니다.

③ 유한 재시도로 무한루프 방지

반려되면 최대 1회만 자동으로 다시 제안받습니다. 그래도 통과하지 못하면 판단을 그대로 사람에게 넘깁니다. "AI 검증도 완벽하지 않다"는 전제를 시스템 설계에 명시적으로 반영한 것입니다.

05 · 직접 조작해보기

외기온과 전력가격을 바꾸면 추천이 어떻게 달라질까

아래 계산은 실제 워크플로우의 Trade-off Optimization Engine 노드와 동일한 공식입니다. 슬라이더를 움직이면 100% / 70% / 40% 출력과 정지(0%) 네 시나리오가 실시간으로 다시 계산됩니다.

06 · 확장 설계

고정된 판단 도구에서, 대화하고 교체 가능한 시스템으로

01

대화형 재시뮬레이터

지금은 슬라이더로 제한했지만, "외기온이 5도 더 오르면?" 같은 자연어 질문을 Trade-off 엔진이 즉시 재계산해 새 시나리오로 보여주는 구조로 확장하도록 설계했습니다.

02

고장예측 알고리즘 플러그인 구조

지금의 고장확률 배수함수 \(M(r)=e^{K(r-1)}\)는 "70% 출력 시 고장확률이 정격 대비 약 11%"라는 단일 앵커 가정에서 역산한 근사식이며, 코드 주석에 그 한계를 명시했습니다. 이 함수를 교체 가능한 플러그인으로 분리하면 설비별·제조사별 실측 열화모델이나 딥러닝 기반 PHM 알고리즘으로 손쉽게 교체·비교 실험할 수 있도록 처음부터 인터페이스를 나눠 설계했습니다.

03

사용자 선택 데이터 적재 → 개인화

운영자가 Slack에서 실제로 어떤 비율을 선택했는지(AI 1순위 제안을 따랐는지, 더 보수적/공격적으로 갔는지) 누적 저장하면, 이후 AI 제안 자체를 그 운영자·설비의 리스크 성향에 맞게 개인화할 수 있습니다.
